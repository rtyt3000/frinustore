# ТЗ: бот-менеджер маркета плагинов Inugram

Канал: https://t.me/frinu_store (публичный). Клиент-плагин: `src/market`, схема каталога: `src/shared/catalog.ts`.
Бот принимает плагины от пользователей, публикует файлы в канал и поддерживает `catalog.json`.

## 1. Стек
- TypeScript, grammY (Bot API), хостинг **Vercel** (см. раздел 13). Postgres (Neon) как **источник истины**.
- Канал и закреплённый `catalog.json` — только выходной артефакт, бот никогда не читает из него состояние.
- Бот — администратор канала (публикация, редактирование, закрепление). Токен и ID админов — в `.env`.

## 2. Роли
- **Пользователь** — любой, кто пишет боту в личку.
- **Автор** — владелец плагина (определяется по `id` плагина, привязка к Telegram user id при первой публикации).
- **Модератор** — user id из `ADMIN_IDS`.

## 3. Формат плагина и источник метаданных
Файл — один `*.inu.js`, UTF-8, до 5 МБ. Бот **не полагается** на заголовок `==InuPlugin==`: все данные каталога (id, имя, версия, описание, иконка, автор) хранятся в БД бота и вводятся автором в меню. Файл для бота — непрозрачный blob.
- Заголовок разбирается по возможности (`best-effort`) и только для: предзаполнения полей мастера публикации, подсказки «версия в файле отличается от введённой», списка грантов для модерации (п. 5). Не разобрался — не ошибка, поля вводятся вручную.
- Из файла берём только технические вещи: размер, `sha256`, признак, что это текст/JS, а не бинарь.
- Поля мастера публикации: **id** (в маркете, `[a-z0-9._-]{3,64}`, уникален), **название** (≤ 40), **версия** (semver, строго больше текущей), **описание** (≤ 500, опционально `ru`/`en`), **иконка** (формат манифеста Inugram, по умолчанию `inu://bot`), **changelog** (≤ 300). Автор (`author`) = отображаемое имя автора, по умолчанию из профиля Telegram, меняется в меню.
- Предупреждение, не блокировка: если в заголовке файла есть `@id` и он не совпадает с id в маркете (или у новой версии `@id` отличается от предыдущей) — показать «приложение поставит это как другой плагин, а не обновит старый». Id внутри файла определяет, обновит ли приложение установленный плагин, поэтому автору надо держать его неизменным; бот этого не навязывает.
- Гранты в `catalog.json` не публикуются как достоверные: их показывает само приложение при установке из файла. Поле `grants` в каталоге — только справочное, из заголовка, и может отсутствовать.

## 4. Сценарии пользователя
Управление — через меню на inline-кнопках (раздел 14); команды остаются как быстрый вход. Свободный текст бот ждёт только на шагах, где это явно запрошено.
1. `/start` — краткая справка.
2. **Отправка плагина** (мастер на inline-кнопках): пользователь шлёт `.inu.js` документом, затем бот по шагам запрашивает/подтверждает id, название, версию, описание, иконку, changelog (каждый шаг с предзаполненным значением из заголовка, если он есть, кнопки «Оставить» / «Изменить» / «Отмена»). Бот:
   1. скачивает файл, считает `sha256`, пробует разобрать заголовок только для предзаполнения (ошибка парсинга не блокирует);
   2. проверяет валидацию (п. 5);
   3. если `id` новый — создаёт плагин, автор = отправитель; если `id` существует и автор совпадает — это новая версия; иначе отказ «id занят»;
   4. версия должна быть строго больше текущей (semver); та же или меньшая — отказ;
   5. спрашивает changelog (необязательно, можно «пропустить»);
   6. показывает карточку: имя, версия, grants (с пометкой опасных `unsafe.*`), кнопки «Опубликовать» / «Отмена».
3. `/my` — список своих плагинов, по каждому: версии, установки, кнопки «Новая версия», «Скрыть версию», «Удалить плагин».
4. `/describe` — смена описания/иконки плагина (описание строкой или `ru`/`en`; иконка в формате манифеста).
5. Все действия над чужим плагином запрещены.

## 5. Валидация и модерация
- Размер, кодировка UTF-8, формат введённых полей, уникальность `id`+`version`, повтор по `sha256`.
- Автопометка рисков по грантам из заголовка (если разобрался): `unsafe.*`, `unsafe.jvm`, `unsafe.xposed`, `fetch` без хоста, `invokeRpc` без scope. Если заголовок не разобран — заявка всегда идёт на ручную модерацию с пометкой «гранты неизвестны».
- Режим модерации (`MODERATION=on|off`, по умолчанию on): новая публикация и любая версия с `unsafe.*` уходит модераторам с кнопками «Одобрить» / «Отклонить + причина». Пока не одобрено — в канал не попадает. Остальные версии уже одобренного плагина того же автора без новых `unsafe.*` публикуются сразу.
- Бан автора (`/ban <user_id>`), скрытие/удаление плагина модератором.
- Лимиты: не более N публикаций в сутки на пользователя (по умолчанию 10).

## 6. Публикация в канал
1. `sendDocument` файла в канал, подпись: `#plugin <name> <version>\n<id>`; полученный `message_id` = `msgId` версии.
2. Пересборка `catalog.json` из БД: только одобренные и не скрытые версии.
3. Обновление закрепа: `editMessageMedia` у закреплённого сообщения с `catalog.json` (так закреп и ссылка стабильны). Если закрепа нет — отправить и `pinChatMessage`.
4. Удаление/скрытие версии: `deleteMessage` файла + пересборка каталога. Нельзя оставлять в каталоге версию, чей файл удалён.
5. Публикация атомарна: при ошибке на любом шаге — откат (удалить загруженный файл), пользователю сообщение об ошибке.
6. Обновления каталога сериализуются очередью (одновременно не более одной пересборки).

## 7. catalog.json
Строго по `src/shared/catalog.ts`:
```json
{
  "schema": 1,
  "updatedAt": 1760000000,
  "plugins": [{
    "id": "rtyt3000.frinumarket",
    "name": "Plugin market",
    "author": "rtyt3000",
    "description": {"en": "...", "ru": "..."},
    "icon": "inu://bot",
    "installs": 0,
    "versions": [{"version": "0.1.0", "msgId": 42, "date": 1760000000, "changelog": "...", "grants": ["account.read(peers)"]}]
  }]
}
```
- Компактный JSON, документ с именем `catalog.json`, размер < 1 МБ (клиент качает его целиком при каждом открытии).
- Все поля берутся из БД бота (введены автором), не из файла. `author` — отображаемое имя, не Telegram id. `grants` в версии опционален и справочный.
- Плагины в порядке: по убыванию `installs`, затем по дате.

## 8. Счётчик установок (inline-запрос)
Кнопок в канале нет. Клиентский плагин при нажатии «Установить» сам шлёт боту inline-запрос (`messages.getInlineBotResults`), бот его записывает.
- В BotFather включить inline mode (`/setinline`), placeholder любой; inline feedback не нужен.
- Формат запроса: `install <plugin_id> <version>` (строка ≤ 256 символов). Любой другой запрос — ответ пустым результатом без записи.
- Обработка `inline_query`: `from.id` + `plugin_id` -> `INSERT INTO installs ... ON CONFLICT DO NOTHING` (уникально по пользователю и плагину). Плагин и версия должны существовать в БД и быть одобренными, иначе игнор.
- **Всегда** отвечать `answerInlineQuery` с пустым `results`, `cache_time: 0`, `is_personal: true` и только потом (или параллельно) писать в БД; на запись ошибка не должна ломать ответ. Telegram ждёт ответ несколько секунд.
- `installs` в `catalog.json` обновляется батчем (cron / `jobs`, раздел 13), не на каждый запрос.
- Метрика защищена слабо (пользователь может слать запросы вручную): это допустимо для v1; уникальность по `user_id` ограничивает накрутку одним зачётом на аккаунт.
- Установка из клиента не блокируется, если бот недоступен (плагин ловит ошибку молча).

## 9. БД (Postgres, Neon через Vercel Marketplace)
- `users(id, banned, created_at)`
- `plugins(id TEXT PK, owner_user_id, name, author, description_json, icon, hidden, created_at)`
- `versions(plugin_id, version, msg_id, date, changelog, grants_json, status[pending|approved|rejected|hidden], file_sha256)`
- `installs(plugin_id, user_id, created_at)` unique(plugin_id,user_id)
- `meta(key, value)` — id закреплённого сообщения каталога.
Миграции — простые SQL-файлы. Доп. таблица `sessions(user_id, state, payload_json, updated_at)` — шаги диалога (ожидание changelog, подтверждение), т.к. память между вызовами функции не живёт.

## 10. Нефункциональное
- Webhook на Vercel (раздел 13), long polling только для локальной разработки.
- Логи структурированные; ошибки публикации — модераторам в личку.
- Резервная копия: команда `/backup` (модератор) присылает JSON-дамп таблиц (`pg_dump` на serverless недоступен).
- Команда `/rebuild` (модератор) — принудительная пересборка каталога из БД.
- Идемпотентность: повторная отправка одного файла (`sha256`) не создаёт дубль.
- Тесты: парсер заголовка, semver-сравнение, сборка каталога, проверка прав.

## 11. Вне v1
Рейтинги/отзывы, поиск, категории, веб-панель, подпись плагинов, автоматическая статическая проверка кода.

## 12. Критерии приёмки
- Загрузка валидного `.inu.js` проходит весь путь до появления версии в `catalog.json` и файла в канале.
- Чужой `id` публиковать нельзя; версия не выше текущей отклоняется.
- Невалидный/превышающий лимит файл отклоняется с понятной причиной.
- Удаление версии убирает её из канала и каталога.
- Клиент `src/market` открывает каталог без изменений схемы.

## 13. Деплой на Vercel

### Архитектура
- Бот — serverless-функция `api/webhook.ts` (Bun runtime: `"bunVersion": "1.x"` в `vercel.json`, либо Node 22 — выбрать один и не смешивать). grammY через `webhookCallback(bot, "std/http")`.
- Webhook регистрируется скриптом `bun run set-webhook` (`setWebhook` с `secret_token`, `allowed_updates: ["message","callback_query","inline_query"]`, `drop_pending_updates` при смене). Функция отклоняет запросы без верного заголовка `X-Telegram-Bot-Api-Secret-Token` (401).
- Файловая система эфемерна: SQLite и локальные файлы **не использовать**. Файл плагина скачивается в память (`getFile` -> fetch, лимит Bot API 20 МБ, наш лимит 5 МБ) и сразу отправляется в канал по `file_id` / буфером.
- Состояние диалога и очередь пересборки — только в Postgres.

### Ограничения и решения
| Проблема | Решение |
| --- | --- |
| Таймаут функции (Hobby 10–60 с, зависит от плана) | Webhook отвечает быстро; тяжёлая публикация (отправка файла, пересборка каталога) укладывается в один вызов, при `maxDuration` в `vercel.json` выставить максимум плана. Если не укладывается — публикация ставится в таблицу `jobs`, обрабатывается cron-ом |
| Параллельные вызовы | Пересборка каталога под `pg_advisory_lock` (или `SELECT ... FOR UPDATE` на строке `meta`); при занятом локе — поставить `jobs(type='rebuild')` и выйти |
| Повторная доставка апдейта Telegram | Таблица `processed_updates(update_id PK)`; повтор игнорируется. Отвечать 200 даже при ошибке бизнес-логики (иначе Telegram будет ретраить) |
| Холодный старт | Минимум зависимостей, соединение с БД через pooled URL / `@neondatabase/serverless`, клиент создаётся на уровне модуля |
| Фоновая батч-задача (`installs` раз в 10 мин) | Vercel Cron -> `api/cron/flush.ts`, защита заголовком `Authorization: Bearer $CRON_SECRET`. На Hobby cron только раз в сутки — тогда либо Pro, либо обновлять каталог при каждой публикации + суточный cron |
| Rate limit Telegram (editMessageMedia закрепа) | Дебаунс: `jobs` с коалесингом (несколько запросов на пересборку = одна пересборка) |

### Конфигурация (Environment Variables)
`BOT_TOKEN`, `WEBHOOK_SECRET`, `CRON_SECRET`, `DATABASE_URL`, `CHANNEL_ID` (числовой `-100…`), `CHANNEL_USERNAME=frinu_store`, `ADMIN_IDS`, `MODERATION`, `DAILY_LIMIT`. Секреты только в Vercel, локально `.env` в `.gitignore`.

### Структура репозитория бота
```

api/cron/flush.ts     # батч installs + выполнение jobs
src/bot.ts            # grammY: команды, сценарии
src/plugin-header.ts  # парсер заголовка + тесты
src/catalog.ts        # сборка catalog.json (типы из схемы клиента)

```

### CI/CD
- Деплой из GitHub: preview на PR, production с `main`. Preview-деплои используют **отдельного тестового бота и тестовый канал** (отдельные env для Preview), чтобы не писать в боевой канал.
- Миграции: `bun run migrate` как шаг build-команды (идемпотентные, с таблицей версий).
- После деплоя `set-webhook` на production URL (вручную или `postbuild` только для Production).

### Приёмка деплоя
- `getWebhookInfo` без `last_error_message`, 200 на валидный апдейт, 401 без секрета.
- Публикация плагина через задеплоенный бот доходит до обновлённого закрепа.
- Два одновременных апдейта не портят `catalog.json` (проверить нагрузочным скриптом из двух параллельных публикаций).
- Повторная доставка того же `update_id` не создаёт дубль версии.

## 14. Меню на inline-кнопках

### Принципы
- Один «экран» = одно сообщение, которое бот **редактирует** (`editMessageText`/`editMessageReplyMarkup`), а не шлёт новое. Каждый экран, кроме главного, имеет «‹ Назад» и «⌂ Меню».
- `/start` и `/menu` показывают главное меню. Любая команда открывает соответствующий экран.
- `callback_data` ≤ 64 байт: формат `<экран>:<действие>:<арг>`, например `p:open:42`, `v:hide:42:3`. Длинные id (`@id` плагина) не класть, использовать числовой `plugins.rowid`/`versions.rowid` из БД. Обязательно `answerCallbackQuery` на каждый клик.
- Протухшие кнопки (старое сообщение, плагин удалён, нет прав) — alert «Устарело, откройте меню заново» и перерисовка главного экрана. Права проверять на **каждом** callback, а не только при показе кнопки.
- Состояние ожидания текста/файла хранится в `sessions` (раздел 9), у шага есть TTL 15 минут и кнопка «Отмена».

### Дерево экранов
```
Главное меню
├─ 📤 Опубликовать плагин     -> «пришлите .inu.js» [Отмена] -> карточка -> [Опубликовать] [Отмена]
│                                 (после файла: [Добавить changelog] [Пропустить])
├─ 📦 Мои плагины             -> список (пагинация ‹ 1/3 ›) -> экран плагина
│     └─ Экран плагина: имя, автор, версии, установки
│        [Новая версия] [Описание] [Иконка] [Версии] [Удалить]
│        └─ Версии: список [Скрыть/Показать] [Удалить] (подтверждение «Да / Нет»)
│        └─ Удалить плагин: подтверждение
├─ ℹ️ Помощь                  -> формат заголовка, гранты, правила, [Открыть канал]
└─ 🛡 Модерация (только ADMIN_IDS)
      ├─ Очередь заявок (пагинация) -> карточка [Одобрить] [Отклонить + причина]
      ├─ Все плагины (скрыть/удалить)
      ├─ Баны (список, [Разбанить]; бан по user_id вводом)
      └─ Сервис: [Пересобрать каталог] [Бэкап] [Статус webhook]
```
- Кнопка «Мои плагины» показывается всем; «Модерация» — только модераторам (иначе скрыта, не просто неактивна).
- Опасные действия (удаление плагина/версии, бан) — всегда с экраном подтверждения.
- Карточка заявки у модератора дублируется ссылкой на файл в служебном канале/чате (`MOD_CHAT_ID`), кнопки работают и оттуда; после решения кнопки заменяются статусом «Одобрено @mod / Отклонено: причина», автору уходит уведомление.

### Критерии приёмки
- Весь функционал из раздела 4 достижим только кнопками, без запоминания команд.
- Клик по кнопке из чужого меню/старого сообщения не выполняет действие (проверка прав и существования).
- Нет «залипших» состояний: «Отмена» и TTL всегда возвращают в главное меню.
- Пагинация корректна на 0, 1, 8 и 50 элементов (по 8 на страницу).
